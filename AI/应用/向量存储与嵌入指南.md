# 向量存储与嵌入指南：从原理到运维

> 向量库持久化与 Embedding 维度管理是 RAG 系统长期稳定运行的基础设施。本文系统梳理了向量库持久化的整体架构、核心组件、维度冲突的根因与修复方案、测试体系与日常运维指南。

---

## 一、为什么需要持久化

### 1.1 核心问题

在 RAG 系统中，向量库的作用是将文档转换为向量并存储，以便后续通过语义检索召回相关内容。如果不做持久化，每次系统重启都需要重新解析文档、重新计算 Embedding、重新构建向量索引——这会带来两个严重问题：

1. **启动时间过长**：大型文档集的 Embedding 计算可能需要数分钟甚至数十分钟。
2. **资源浪费**：每次重启都重复相同的计算，浪费 CPU 和 API 调用额度。

### 1.2 持久化的价值

| 维度 | 无持久化 | 有持久化 |
|------|---------|---------|
| 启动速度 | 每次数分钟 | 秒级加载 |
| 知识延续性 | 重启即丢失 | 跨会话保留 |
| 共享记忆 | 无法跨 Agent 复用 | 多 Agent 共同沉淀 |
| 运维成本 | 高 | 低 |

## 二、整体架构设计

本项目采用 **双库分离** 的持久化策略，将主知识库与共享记忆库分开管理：

```
┌──────────────────────────────────────────────────────────────────┐
│                        向量库持久化体系                            │
├────────────────────────────┬─────────────────────────────────────┤
│     主知识库（RAG）          │       共享记忆库（SharedMemory）      │
│   chroma_db_unified/       │    chroma_db_shared_memory/         │
│   ─────────────────        │    ────────────────────────         │
│   来源：PDF 文档解析          │    来源：多 Agent 对话中提取的知识      │
│   构建：build_or_load()    │    构建：SharedMemoryStore.store()   │
│   用途：医学知识检索增强       │    用途：跨会话知识沉淀与复用           │
│   触发：系统启动 / 手动脚本    │    触发：每次 Agent 产生有价值输出       │
├────────────────────────────┴─────────────────────────────────────┤
│                  底层：ChromaDB（PersistentClient）                │
│                Embedding：XfyunEmbeddings（1024d BGE）             │
│                 过滤：MetaMemoryFilter（熵值阈值 0.85）              │
│                 共识：ConsensusEngine（冲突解决）                    │
│                 信誉：AgentReputationStore（JSON 持久化）            │
└──────────────────────────────────────────────────────────────────┘
```

**设计理念**：

- **主知识库**：存放从 PDF 文档中提取的静态知识，内容相对稳定，在文档更新时重建。
- **共享记忆库**：存放多 Agent 协作过程中动态产生的知识洞察，持续积累，用熵值过滤保证质量。

## 三、核心组件详解

### 3.1 XfyunEmbeddings — 双通道 Embedding 引擎

XfyunEmbeddings 是整个向量体系的发动机，负责将文本转换为向量。

**调用链：**

```
embed_query / embed_documents
  → 讯飞 API（HMAC-SHA256 签名鉴权）
  → 调用失败？→ _xfyun_dead = True
  → _get_fallback_embeddings()
  → 本地 BGE-large-zh-v1.5（1024d，CPU 推理）
```

**关键设计机制：**

| 机制 | 说明 |
|------|------|
| 签名鉴权 | `_embed_once()` 内使用 HMAC-SHA256，携带 `X-App-Id` 等 4 个请求头 |
| QPS 节流 | `_throttle()` 类方法，`_last_request_time` 类变量，请求间隔 ≥ 0.7s |
| 错误分级 | `_FATAL_ERROR_CODES` 字典，错误码 11200/11201/10001 等标记为不可重试 |
| 批量降级 | 单条失败时整批统一降级，避免同一批次中出现维度混用 |
| 重试策略 | 指数退避 `1.5 × (attempt + 1)` 秒，最多重试 4 次 |

**BGE 模型类级缓存（核心优化）：**

```python
# 修复前：实例变量，每次实例化都重新加载 1.3GB 模型
self._fallback_embeddings = None

# 修复后：类变量，全进程共享一份
_fallback_embeddings_cache = None
_fallback_embeddings_failed = False

@classmethod
def _get_fallback_embeddings(cls):
    if cls._fallback_embeddings_cache is not None:
        return cls._fallback_embeddings_cache
    if cls._fallback_embeddings_failed:
        return None
    cls._fallback_embeddings_cache = HuggingFaceBgeEmbeddings(...)
    return cls._fallback_embeddings_cache
```

**效果**：第二次及之后实例化 `XfyunEmbeddings()` 从 185 秒降至 0 秒。

### 3.2 SharedMemoryStore — 共享记忆存储

多 Agent 共享知识记忆库，实现跨会话的知识沉淀。

- `store()`：将 Agent 的知识洞察存入向量库，附带元数据（来源 Agent、时间戳、置信度）。
- `search()`：基于语义相似度检索历史记忆，辅助当前决策。
- 基于 ChromaDB PersistentClient，自动持久化到磁盘。

### 3.3 MetaMemoryFilter — 元记忆过滤器

并非所有 Agent 输出都值得存入记忆。MetaMemoryFilter 通过 **信息熵** 评估内容价值：

```python
class MetaMemoryFilter:
    def __init__(self, entropy_threshold=0.85):
        self.threshold = entropy_threshold

    def filter(self, items):
        return [item for item in items
                if self._calculate_entropy(item.content) < self.threshold]
```

**设计原理**：熵值越高，信息越"泛"（如"你好"、"收到"等通用回复），缺乏存储价值；熵值越低，信息越具体，具有长期参考意义。

### 3.4 ConsensusEngine — 共识引擎

当多个 Agent 对同一问题给出不同建议时，通过投票机制解决冲突。

```python
advices = {
    "agent_a": "建议从 Willis 环解剖开始...",
    "agent_b": "建议从 Willis 环解剖开始...",
    "agent_c": "跳过解剖，直接学指南...",
}

result = ConsensusEngine().resolve_conflict(advices)
# → winning_agents: ["agent_a", "agent_b"]
# → reached: False（未达 100% 共识）
```

### 3.5 AgentReputationStore — Agent 信誉存储

追踪每个 Agent 的信誉分数，以 JSON 文件持久化。

```python
store = AgentReputationStore(config={"reputation_file": "agent_reputation.json"})
store.update("agent_a", was_correct=True)
store.update("agent_a", was_correct=False)
score = store.get_score("agent_a")  # 0.5 (1/2)
```

### 3.6 build_or_load_vectorstore — 主知识库构建入口

主知识库的构建与加载入口，自动判断是否需要重建。


## 四、Embedding 模型与维度

### 4.1 背景概念

**Embedding（文本向量化）** 是将文本转换为固定长度浮点数数组（向量）的过程。核心特性：**语义相近的文本，在向量空间中距离也相近**。

**维度（Dimension）** 是向量数组的长度，由 Embedding 模型决定。**不同模型产出的向量维度不同，无法混用**。

**ChromaDB** 关键约束：一个集合创建后维度就固定了，后续写入的向量必须与创建时维度一致，否则直接报错。

### 4.2 三种模型的对比

| 对比维度 | 讯飞云端 API | BGE-large-zh-v1.5 | ONNX 默认 |
|----------|-------------|-------------------|-----------|
| 向量维度 | 2560 | 1024 | 384 |
| 运行位置 | 云端 | 本地 CPU | 本地 CPU |
| 中文语义质量 | 高 | 高（中文专项优化） | 中 |
| QPS 限制 | ≈2（免费档） | 无限制 | 无限制 |
| 模型大小 | 无本地占用 | ~1.3GB | ~90MB |

### 4.3 推荐策略

**生产环境建议使用 `XFYUN_EMBEDDING_ENABLED=false`，全程使用本地 BGE（1024d）**：

1. 免费档 QPS ≈ 2，多专家并行推理时极易触发限流
2. 本地推理无网络延迟，稳定性更高
3. BGE 模型在中文语义任务上表现优异

### 4.4 维度一致性保证

**核心原则：所有向量库必须使用同一份 Embedding 模型（1024d BGE），否则检索结果不可比。**

```
XfyunEmbeddings（1024d BGE）
  ├── _ChromaEmbeddingFunction 包装
  │     ├── SharedMemoryStore → chroma_db_shared_memory
  │     └── build_or_load_vectorstore → chroma_db_unified
  └── 直接调用
        ├── embed_query() → 检索用
        └── embed_documents() → 入库用
```

## 五、维度不匹配的根因分析

### 5.1 问题表现

```
chromadb.errors.InvalidDimensionException:
Embedding dimension 1024 does not match collection dimensionality 2560
```

### 5.2 为什么维度会变

`XfyunEmbeddings` 封装了**自动降级**逻辑：

```
                 ┌─ 讯飞 API 正常 ──→ 2560d
                 │
XfyunEmbeddings ─┤
                 │                 ┌─ 成功 → BGE 1024d
                 └─ 讯飞 API 失败 ──┤
                                   └─ 失败 → ChromaDB 默认 ONNX 384d
```

一旦降级触发，产出的向量维度就变了，与旧数据冲突。

### 5.3 典型触发场景

**场景一：首次构建用了讯飞 2560d，后续降级到 BGE 1024d**

```
T1: 讯飞 API 正常 → 向量库以 2560d 创建
T2: 讯飞 API 欠费/限流 → 降级到 BGE 1024d → 写入 1024d 向量 → 报错！
```

**场景二：ChromaDB 未传 embedding_function，使用了内置 ONNX 384d**

```python
# 危险写法
collection = client.get_or_create_collection(name="my_collection")

# 安全写法
collection = client.get_or_create_collection(
    name="my_collection",
    embedding_function=my_embedding_function
)
```

## 六、修复方案

### 6.1 核心修复：`_ChromaEmbeddingFunction` 包装器

```python
class _ChromaEmbeddingFunction:
    def __init__(self, xfyun_embeddings):
        self._xfyun = xfyun_embeddings

    def __call__(self, texts):
        if isinstance(texts, str):
            return [self._xfyun.embed_query(texts)]
        return self._xfyun.embed_documents(texts)
```

### 6.2 显式传入 embedding_function

```python
# 修复前（危险）
self._collection = client.get_or_create_collection(
    name=self.COLLECTION_NAME,
    metadata={"hnsw:space": "cosine"},
)

# 修复后（安全）
self._collection = client.get_or_create_collection(
    name=self.COLLECTION_NAME,
    embedding_function=self._ef,
    metadata={"hnsw:space": "cosine"},
)
```

### 6.3 降级存储路径优化

维度冲突时跳过无效重试，直接给出修复指引：

```python
if "dimension" in err_msg.lower():
    logger.error(
        f"[shared_memory] 向量维度冲突，无法存储: {err_msg}\n"
        f"   解决：删除向量库目录后重启服务，统一使用一种 embedding 模型。\n"
        f"   建议：在 .env 中设置 XFYUN_EMBEDDING_ENABLED=false"
    )
    return None
```

### 6.4 配置文件修改

```bash
# .env
XFYUN_EMBEDDING_ENABLED=false
```

### 6.5 部署前必须执行的步骤

```bash
rm -rf model/data/vector_stores/chroma_db_unified
rm -rf model/data/vector_stores/chroma_db_shared_memory
```

重启服务后，系统会自动用 1024d 统一维度重建。

## 九、常见问题与解决方案

| 问题 | 根因分析 | 解决方案 |
|------|----------|----------|
| ChromaDB 初始化失败 | `__call__(texts)` 参数名与 ChromaDB 内部调用不匹配 | 改为 `__call__(input)` 以兼容 ChromaDB 接口 |
| BGE 模型重复加载 | 实例变量无法跨实例共享 | 改为类级别 `_fallback_embeddings_cache` |
| 向量维度不一致 | 旧库用 ONNX-384d，新库用 BGE-1024d | 删除旧库目录，用统一维度重建 |
| 运行时静默"假死" | BGE 首次下载约 3 分钟，期间无日志输出 | main.py 启动时主动调用 `preload_fallback()` |
| Windows 清理报 PermissionError | ChromaDB 文件锁未释放 | 重启进程后清理，或忽略该错误 |
